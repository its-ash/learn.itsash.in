13 — Kernel & Modules

The kernel is the core of Linux — it manages the CPU, memory, devices, filesystems, and processes. This chapter covers kernel versions, the module system (loadable drivers), kernel parameters (sysctl), /proc and /sys interfaces, and how to update/compile a kernel. You don't need to be a kernel developer to be a proficient Linux user, but understanding these concepts is essential for troubleshooting, performance tuning, and hardware support.

Kernel Versions

bash
uname -r              # current kernel release (e.g., 6.8.0-31-generic)
uname -a              # full info (hostname, kernel version, arch, build date)
cat /proc/version      # kernel version + gcc version it was built with
hostnamectl            # distro + kernel + arch (systemd)
``
::

Version numbering (modern, since Linux 4.0):

```text
6.8.0-31-generic
└┘└┘└┘ └┘ └─────┘
 │ │  │  │     └ distro/build flavor (Ubuntu: -generic, -aws, -azure; RHEL: -el9)
 │ │  │  └ patch level (distro-specific numbering)
 │ │  └ minor (was even=stable, odd=dev — abolished in 2.6; now all releases are stable)
 │ └ major
 └ mainline version
  • Mainline kernels (kernel.org): 6.8, 6.9, ... — released every ~9 weeks.
  • Distro kernels: Ubuntu/RHEL patch and backport fixes onto a base version. 6.8.0-31-generic is Ubuntu's 31st patch level of 6.8.
  • LTS (Long Term Support): some mainline versions get long support (e.g., 6.1, 6.8). Distros often pick LTS bases.

Where the Kernel Lives

FileContents
/boot/vmlinuz-<version>The compressed kernel image (booted by GRUB)
/boot/initrd.img-<version> / initramfs-<version>Initial RAM disk (early userspace, loads modules to mount root)
/boot/config-<version>Kernel config (what was enabled at compile time)
/boot/System.map-<version>Symbol table (for debugging)
/lib/modules/<version>/Loadable modules for this kernel version
/proc/Virtual filesystem: kernel/process state
/sys/Virtual filesystem: kernel objects/devices
/dev/Device files (created by udev from kernel events)

Loadable Kernel Modules (LKMs)

Drivers and features can be compiled as modules (.ko files) that are loaded on demand — rather than being built into the kernel. This keeps the kernel image small and allows loading drivers without rebooting.

Module Commands

bash
lsmod                        # list loaded modules
sudo modprobe nfs            # load a module (+ dependencies)
sudo modprobe nfs version=4  # load with parameters
sudo modprobe -r nfs         # remove a module (and deps)
sudo insmod /path/to/driver.ko   # insert a specific .ko file (no deps)
sudo rmmod driver            # remove a module (fails if in use)
modinfo nfs                  # show module info (author, params, deps)
modinfo -p nfs               # parameters only
cat /proc/modules            # loaded modules (like lsmod, raw)
``
  • modprobe is the high-level tool — it resolves dependencies (loading prerequisites). Use it.
  • insmod is low-level — loads a single .ko without dependency resolution. Use only for testing custom modules.
  • rmmod fails if the module is in use (a filesystem is mounted, a device is active). modprobe -r handles cleanup.

Where Modules Live

bash
ls /lib/modules/$(uname -r)/
# build/        ← symlink to kernel headers (for building modules)
# kernel/       ← the modules (.ko files), organized by category
#   drivers/
#   net/
#   fs/
#   crypto/
# modules.dep   ← dependency graph (generated by depmod)
# modules.alias ← aliases (e.g., pci:v00008086... → i915)
``
::

### Module Dependencies

`depmod` generates `modules.dep` (the dependency graph). Run it after adding/removing `.ko` files:

::code-wrapper{language="bash"}
```bash
sudo depmod -a
``

Auto-Loading at Boot

Modules listed in /etc/modules-load.d/*.conf are loaded at boot:

bash
echo "nfs" | sudo tee /etc/modules-load.d/nfs.conf
``
::

Module *parameters* can be set in `/etc/modprobe.d/*.conf`:

::code-wrapper{language="bash"}
```bash
echo "options nfs version=4" | sudo tee /etc/modprobe.d/nfs.conf
``

Blacklisting Modules

Prevent a module from auto-loading (e.g., a problematic driver):

bash
echo "blacklist nouveau" | sudo tee /etc/modprobe.d/blacklist-nouveau.conf
# To fully prevent even manual load:
echo "install nouveau /bin/false" | sudo tee -a /etc/modprobe.d/blacklist-nouveau.conf
``
::

`blacklist` prevents auto-load (by alias), but `modprobe nouveau` still works. The `install ... /bin/false` trick makes even manual load fail.

## Kernel Parameters — `sysctl`

`sysctl` reads and sets tunable kernel parameters at runtime (stored in `/proc/sys/`).

### Reading

::code-wrapper{language="bash"}
```bash
sysctl -a                      # all parameters (huge)
sysctl net.ipv4.ip_forward     # one parameter
cat /proc/sys/net/ipv4/ip_forward   # same (file path = parameter name with / for .)
sysctl -a | grep ipv4 | head
sysctl --system                # load all configs from /etc/sysctl.d/
``

Setting (Temporary)

bash
sudo sysctl -w net.ipv4.ip_forward=1     # set now (lost on reboot)
echo 1 | sudo tee /proc/sys/net/ipv4/ip_forward   # same (write to /proc)
``
::

### Setting (Persistent)

Config in `/etc/sysctl.conf` (legacy) or `/etc/sysctl.d/*.conf` (modern):

::code-wrapper{language="bash"}
```bash
echo "net.ipv4.ip_forward = 1" | sudo tee /etc/sysctl.d/99-ip-forward.conf
sudo sysctl -p /etc/sysctl.d/99-ip-forward.conf   # load just this file
sudo sysctl --system                               # load all
``

Common Parameters

net.ipv4.tcp_keepalive_timeTCP keepalive interval (seconds)
net.core.somaxconnMax backlog of pending connections

kernel.printkConsole log level

/etc/sysctl.d/ Precedence

Files are loaded in lexical order. 99-sysctl.conf is a symlink to /etc/sysctl.conf (loaded last, lowest priority). Use 99-*.conf for your overrides so they take precedence.

### Boot Parameters (`/proc/cmdline`)

The parameters GRUB passed to the kernel at boot:

::code-wrapper{language="bash"}
```bash
cat /proc/cmdline
# BOOT_IMAGE=/boot/vmlinuz-6.8.0-31-generic root=UUID=abc123 ro quiet splash
``

Edit in /etc/default/grub (GRUB_CMDLINE_LINUX_DEFAULT=...), then sudo update-grub (Debian) or sudo grub2-mkconfig -o /boot/grub2/grub.cfg (RHEL).

Common boot params:

  • root=UUID=... — root filesystem.
  • ro — mount root read-only initially (remounted rw later).
  • quiet splash — suppress boot messages (remove for debugging).
  • systemd.unit=rescue.target — boot to rescue mode.
  • init=/bin/bash — bypass init (extreme recovery).
  • nomodeset — don't load graphics drivers (for display issues).
  • acpi=off — disable ACPI (hardware workaround).

/sys — Kernel Object Interface

Recap from chapter 03. Key uses for kernel/module management:

bash
ls /sys/module/                 # all loaded modules (one dir each)
cat /sys/module/nfs/version     # module version
ls /sys/module/nfs/parameters/  # module parameters (runtime values)

ls /sys/class/net/              # network interfaces
cat /sys/class/net/eth0/mtu     # current MTU
echo 9000 | sudo tee /sys/class/net/eth0/mtu  # set MTU (temporary)

ls /sys/devices/                # all devices (hardware tree)
cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor  # CPU governor
``
::

## udev — Device Management

`udev` is the device manager — it listens to kernel events (via netlink) and creates/removes `/dev` entries, runs scripts, and applies rules.

### udev Rules

Rules in `/lib/udev/rules.d/` (package defaults) and `/etc/udev/rules.d/` (admin overrides):

```text
# /etc/udev/rules.d/99-usb-serial.rules
SUBSYSTEM=="tty", ATTRS{idVendor}=="0403", ATTRS{idProduct}=="6001", SYMLINK+="usb_serial"

This creates /dev/usb_serial → the FTDI USB-serial device, stable across reboots (instead of /dev/ttyUSB0 sometimes being ttyUSB1).

udev Commands

bash
udevadm info /dev/sda1              # device info
udevadm info -a /dev/sda1           # all attributes (for writing rules)
udevadm monitor                     # live device events (plug/unplug USB)
udevadm test /sys/block/sda         # test rules for a device
sudo udevadm control --reload-rules  # reload rules after editing
sudo udevadm trigger                # re-process all devices (apply new rules)
``

Kernel Upgrade

Via Package Manager (Most Common)

Distros ship kernel updates as packages:

bash
# Debian/Ubuntu
sudo apt update && sudo apt install linux-image-generic
# Or a specific version:
sudo apt install linux-image-6.8.0-31-generic

# RHEL/Rocky
sudo dnf install kernel
# Or a specific version:
sudo dnf install kernel-6.8.0-31.el9

# Arch (always full-upgrade)
sudo pacman -Syu    # updates kernel along with everything
``
::

After installing, reboot to use the new kernel. Old kernels are kept (so you can fall back). Check:

::code-wrapper{language="bash"}
```bash
dpkg --list | grep linux-image      # Debian (installed kernels)
rpm -qa | grep kernel               # RHEL
ls /boot/vmlinuz-*                  # all installed kernel images
``

Removing Old Kernels

/boot can fill up with old kernels. Clean:

bash
# Debian/Ubuntu (safe — keeps current + one previous)
sudo apt autoremove --purge
# Or specifically:
sudo apt purge linux-image-5.15.0-25-generic   # remove a specific old one

# RHEL
sudo dnf remove --oldinstallonly
# Or:
sudo dnf remove kernel-5.14.0-162.el9

# Check /boot space:
df -h /boot
``
::

**Never remove the running kernel** — check `uname -r` and don't purge that version.

## Building a Custom Kernel (Overview)

For when you need a specific feature, patch, or optimization. Full process:

::code-wrapper{language="bash"}
```bash
# 1. Get the source
git clone https://git.kernel.org/pub/scm/linux/kernel/git/stable/linux.git
cd linux
git checkout v6.8

# 2. Configure (start from current config)
cp /boot/config-$(uname -r) .config
make oldconfig          # interactively ask about new options
# Or:
make menuconfig         # interactive menu (ncurses)
# Or:
make localmodconfig     # only build modules currently loaded (faster)

# 3. Build
make -j$(nproc)         # compile (parallel)

# 4. Install modules + kernel
sudo make modules_install
sudo make install       # copies vmlinuz, System.map, config to /boot, updates GRUB

# 5. Reboot
sudo reboot
``

This is rarely needed on servers (distro kernels are well-tuned). It's common on embedded systems or for specific driver support.

DKMS — Dynamic Kernel Module Support

Third-party modules (e.g., NVIDIA, VirtualBox, ZFS) need to be rebuilt for each kernel version. DKMS automates this:

bash
sudo apt install dkms
sudo dkms install nvidia/550.54          # build + install for current kernel
sudo dkms install nvidia/550.54 -k 6.8.0-31-generic  # specific kernel
dkms status                              # list DKMS modules
sudo dkms remove nvidia/550.54 --all     # remove
``
::

When a new kernel is installed, DKMS automatically rebuilds registered modules for it (via a kernel postinst hook).

## `initramfs` — Early Userspace

The **initramfs** (initial RAM filesystem) is loaded by the bootloader into RAM. It contains enough userspace to:
1. Load modules needed to access the root filesystem (storage drivers, filesystem drivers).
2. Mount the root filesystem.
3. `pivot_root` into it and `exec` the real init (systemd).

Without an initramfs, the kernel needs all drivers built-in (not modules). With it, drivers can be modules — the initramfs loads them before root is mounted.

### Regenerating initramfs

After kernel or storage changes:

::code-wrapper{language="bash"}
```bash
sudo update-initramfs -u        # Debian/Ubuntu (current kernel)
sudo update-initramfs -u -k all # all kernels
sudo dracut -f                  # RHEL/Fedora
sudo mkinitcpio -P              # Arch
``

This is required after:

  • Changing storage drivers (e.g., adding LVM/RAID to a new kernel).
  • Adding modules to the initramfs config.
  • DKMS changes that affect early boot.

Troubleshooting Kernel Issues

Kernel Panics

A kernel panic is an unrecoverable kernel error. The system halts and prints a stack trace. Common causes:

  • Missing or mismatched kernel modules in initramfs (can't mount root).
  • Bad RAM (hardware).
  • OOM with no recoverable memory.
  • Driver bug.

If the panic is at boot ("unable to mount root fs"), boot an older kernel (GRUB → "Advanced options") and rebuild the initramfs.

dmesg for Kernel Errors

bash
dmesg --level=err,crit,alert,emerg
dmesg -T | grep -i "error\|fail\|warn"
journalctl -k -p err          # same, from journald
``
::

### Module Won't Load

::code-wrapper{language="bash"}
```bash
sudo modprobe -v module_name   # verbose (shows what it's trying)
sudo modprobe --force-vermagic module_name   # bypass version check (DANGEROUS)
dmesg | tail                   # see why it failed
modinfo module_name            # check version, kernel it was built for
``

Common cause: the module was built for a different kernel version (vermagic mismatch). Rebuild with DKMS or against the correct kernel headers.

💡 Tips & Tricks

  • Idiom: use sysctl --system after editing /etc/sysctl.d/*.conf — loads all sysctl files in order. Avoid sysctl -p alone (loads only /etc/sysctl.conf). -p <file> loads a specific file.
  • Idiom: put custom sysctl in /etc/sysctl.d/99-*.conf — files load in lexical order, so 99- runs last and wins. Never edit /etc/sysctl.conf directly on modern distros (it's a legacy file, overridden by sysctl.d/).
  • Idiom: use modprobe (not insmod) for loading modules — modprobe resolves dependencies (loads prerequisites automatically). insmod loads a single .ko and fails if deps are missing. Use insmod only for testing custom modules.
  • Idiom: use modinfo <module> before loading — shows the module's description, parameters, dependencies, and which kernel it was built for. Reveals if a parameter exists before you try to set it.
  • Idiom: blacklist problematic modules in /etc/modprobe.d/blacklist-*.conf — e.g., blacklist nouveau before installing NVIDIA drivers. blacklist stops auto-load; add install <module> /bin/false to block even manual loading.
  • Idiom: run sudo update-initramfs -u (or dracut -f) after storage/kernel changes — ensures the initramfs has the modules to boot. Forgetting this is a common cause of "can't boot after kernel update" (missing storage driver in initramfs).
  • Debug: use udevadm monitor to watch device events live — plug in a USB device and see the kernel + udev events. Essential for debugging "my device isn't detected" or "the /dev node isn't created."
  • Debug: use cat /proc/cmdline to verify boot parameters — confirms that GRUB_CMDLINE_LINUX changes took effect after update-grub. If a param is missing, GRUB config wasn't regenerated or the wrong file was edited.
  • Debug: use journalctl -k -p err (or dmesg --level=err) for kernel errors — shows hardware failures, driver issues, OOM kills. The kernel log is the first place to look for "the system is acting weird."

⚠️ Edge Cases & Gotchas

  • Modules are kernel-version-specific: a module built for 6.8.0-31 won't load on 6.8.0-32 (vermagic check). DKMS rebuilds modules on kernel updates — if DKMS fails (e.g., NVIDIA driver can't build against a new kernel), the module won't load after reboot. Check dkms status after kernel updates.
  • rmmod fails if the module is in use: you can't remove a filesystem module while a filesystem of that type is mounted, or a network driver while the interface is up. Stop the usage first (umount, ip link set down), then rmmod.
  • sysctl -w changes are temporary: they're lost on reboot. Always persist in /etc/sysctl.d/. The common mistake is sudo sysctl -w vm.swappiness=10 and expecting it to survive a reboot.
  • /proc/sys/ writes are immediate but not atomic: writing to /proc/sys/net/ipv4/ip_forward takes effect instantly, but a concurrent reader might see a partial value. Use sysctl (which handles this) rather than raw echo > /proc/sys/....
  • Removing the running kernel breaks the system: if you apt purge linux-image-$(uname -r), the running kernel's files are deleted. The system may keep running (kernel is in memory), but you can't load modules or rebuild initramfs. Never purge the running kernel — check uname -r first.
  • init=/bin/bash bypasses everything: booting with init=/bin/bash gives a raw root shell with no init, no services, no mounting. Useful for recovery, but easy to make things worse. Remount root read-write (mount -o remount,rw /) before editing files.
  • nomodeset disables graphics acceleration: it's a workaround for display issues (black screen on boot), but it disables KMS (kernel mode setting), so you get software rendering. Use it to boot and fix the driver issue, not as a permanent setting.
  • Custom kernels don't get security updates: if you compile your own kernel, you're responsible for backporting security fixes. Distros' kernels include years of backported patches. Only run a custom kernel if you have a specific reason.
  • /boot can fill up from old kernels: apt keeps old kernels, and /boot is often a small separate partition. df -h /boot filling up causes update failures. Clean with sudo apt autoremove --purge (Debian) or dnf remove --oldinstallonly (RHEL).
  • DKMS can break on kernel updates: if a third-party module (NVIDIA, ZFS) can't compile against a new kernel (API changed), DKMS fails, and after reboot the module is missing (no GUI, no ZFS). Check dkms status and have a fallback kernel before upgrading.
  • /proc and /sys are virtual: du -sh /proc gives nonsense. tar should exclude them (--exclude=/proc --exclude=/sys). Don't try to back them up — they're generated by the kernel at read time.

🧠 Quick Quiz

You install a new kernel via sudo apt install linux-image-6.8.0-35-generic, reboot, and get a kernel panic: "VFS: Unable to mount root fs on unknown-block(0,0)". What's the most likely cause, and how do you fix it?

Answer

The initramfs is missing or doesn't have the storage driver. "Unable to mount root fs" means the kernel booted but can't find/read the root filesystem — because the driver for your disk controller or filesystem (ext4, LVM, NVMe) is a module that wasn't included in the initramfs.

Fix:

  1. Boot an older (working) kernel — GRUB → "Advanced options for Ubuntu" → select the previous kernel (e.g., 6.8.0-31).
  2. Regenerate the initramfs for the new kernel:
bash
sudo update-initramfs -u -k 6.8.0-35-generic
# Or for all kernels:
sudo update-initramfs -u -k all
  1. Reboot into the new kernel.

Why it happens:

  • The kernel package's postinst script usually runs update-initramfs automatically, but it can fail (missing tools, disk full in /boot, interrupted install).
  • If you changed storage config (added LVM, RAID, encrypted root) without regenerating initramfs, the needed modules aren't there.
  • A DKMS failure during kernel install can leave the initramfs incomplete.

Prevention:

  • Check df -h /boot before installing (needs ~50 MB free).
  • After install, verify: ls /boot/initrd.img-6.8.0-35-generic exists and is non-trivial in size.
  • Keep at least one known-good kernel installed as a fallback.

The general lesson: the initramfs must contain all modules needed to mount root. Any change to storage (new disk controller, LVM, encryption, filesystem) requires update-initramfs -u.

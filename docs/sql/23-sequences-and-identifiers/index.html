23 — Sequences & Identifiers

Auto-incrementing IDs are the most common primary key strategy. PostgreSQL has evolved through three mechanisms: SERIAL (legacy), IDENTITY (standard SQL), and SEQUENCE (the underlying primitive). Understanding all three prevents gaps, replication issues, and migration headaches.

SEQUENCE — the primitive

A sequence is a server-side counter, independent of any table:

sql
CREATE SEQUENCE my_seq START 1 INCREMENT 1;

SELECT nextval('my_seq');   -- 1
SELECT nextval('my_seq');   -- 2
SELECT currval('my_seq');   -- 2 (current session's last value)
SELECT lastval();           -- 2 (last sequence used in this session)
``
::

- `nextval` advances and returns the next value.
- `currval` returns the value the *current session* last got from `nextval` (not the global current value — call `nextval` first in the session, or it errors).
- `setval` manually sets the value (for migrations/syncs).

Sequences are **not transactional** — `nextval` is never rolled back. This is by design: if two transactions both get a value and one rolls back, the sequence still advanced, avoiding contention. The cost: **gaps are normal and expected**. A sequence produces unique values, not consecutive ones.

## SERIAL — the legacy shortcut

`SERIAL` is sugar for: create a sequence, set the column's default to `nextval('...')`, and make it `NOT NULL`:

::code-wrapper{language="sql"}
```sql
CREATE TABLE users (
  id SERIAL PRIMARY KEY,
  name TEXT
);
-- Equivalent to:
CREATE SEQUENCE users_id_seq;
CREATE TABLE users (
  id INTEGER NOT NULL PRIMARY KEY DEFAULT nextval('users_id_seq')
);
ALTER SEQUENCE users_id_seq OWNED BY users.id;
``

BIGSERIAL is the same but with bigint (use this — int overflow at ~2.1B is a real risk for high-write tables).

SERIAL gotchas

  • The column's type is integer (or bigint), not "serial" — SERIAL is a declaration-time macro, not a type.
  • The sequence survives even if you drop the default — the sequence isn't dropped until the column is.
  • You can't change the type of a SERIAL column to SERIAL of a different size cleanly — manage the sequence manually.
  • SERIAL isn't standard SQL — it's PostgreSQL-specific (MySQL has AUTO_INCREMENT, SQL Server has IDENTITY).

IDENTITY — the modern standard

GENERATED ... AS IDENTITY (PostgreSQL 10+) is the SQL-standard equivalent of SERIAL, with cleaner semantics:

sql
CREATE TABLE users (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name TEXT
);

-- Or BY DEFAULT (allows manual inserts)
CREATE TABLE users (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  name TEXT
);
``
::

### ALWAYS vs BY DEFAULT

- `GENERATED ALWAYS` — the database always generates the value; manual inserts specifying `id` are **rejected** (unless `OVERRIDING SYSTEM VALUE` is used).
- `GENERATED BY DEFAULT` — the database generates a value if the column is omitted, but **allows manual inserts** (with the risk of collision if the manual value is below the sequence's current position).

`ALWAYS` is safer (prevents accidental collisions from manual inserts); `BY DEFAULT` is more flexible (useful for migrations/data loads).

### Why prefer IDENTITY over SERIAL

- **Standard SQL**: portable to other databases that support the standard.
- **Proper dependency tracking**: the identity is tied to the column; `ALTER TABLE ... DROP COLUMN` cleans up. `SERIAL`'s sequence can be orphaned.
- **Easier alteration**: `ALTER TABLE ... ALTER COLUMN id RESTART WITH 1000` — no manual sequence juggling.
- **Cleaner `pg_dump`/restore**: identities restore correctly; `SERIAL` sequences can get out of sync.

**Use `GENERATED ALWAYS AS IDENTITY` for new tables.** Reserve `SERIAL` for legacy compatibility.

## UUID

For distributed systems, multi-tenant apps, or IDs generated outside the database, use `UUID`:

::code-wrapper{language="sql"}
```sql
CREATE EXTENSION IF NOT EXISTS pgcrypto;

CREATE TABLE events (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  -- ...
);

-- Or in PostgreSQL 13+ (no extension needed)
-- id UUID PRIMARY KEY DEFAULT gen_random_uuid()
``

UUID pros and cons

Pros:

  • Globally unique — no coordination between nodes/services.
  • Non-sequential — can't guess IDs (slight security benefit).
  • Client-side generation — the app can generate the ID before insert (useful for idempotent retries).

Cons:

  • Larger (16 bytes vs 8 for bigint) — larger indexes, more memory.
  • Random distribution — B-tree indexes become fragmented (random inserts), cache locality is poor. Consider UUIDv7 (time-ordered) for indexable UUIDs.
  • Less readable — debugging with UUID PKs is harder than with 1, 2, 3.

For most apps, BIGINT GENERATED ALWAYS AS IDENTITY is the best default. Use UUIDs when you need client-side generation or distributed uniqueness.

Gaps and Resetting

Gaps are normal

Sequences don't fill gaps — a rolled-back insert, a failed insert, or a restart leaves a gap. This is correct (filling gaps would require serialization, killing throughput). Don't try to eliminate gaps; design around them.

Resetting a sequence

After a data load or migration, the sequence might be behind the max ID in the table:

sql
-- Set the sequence to max(id) + 1
SELECT setval(pg_get_serial_sequence('users', 'id'),
              (SELECT MAX(id) FROM users));
-- Or explicitly
SELECT setval('users_id_seq', (SELECT MAX(id) FROM users));
``
::

`setval(seq, N)` sets the sequence so the next `nextval` returns `N+1` (by default — `setval(seq, N, false)` makes the next `nextval` return `N`). Always reset after a bulk load or `COPY` that inserted explicit IDs.

### Restarting an IDENTITY column

::code-wrapper{language="sql"}
```sql
ALTER TABLE users ALTER COLUMN id RESTART WITH 1000;
``

Sequences and Replication

Sequences don't replicate with logical replication — they're per-server state. In a replication setup (primary + replicas):

  • Replicas have their own sequence state, which may lag the primary.
  • On failover, the new primary's sequence might be behind the IDs already issued — causing duplicate key errors.

Fix: after a failover, advance the sequence past the max ID:

sql
SELECT setval('users_id_seq', (SELECT MAX(id) FROM users));
``
::

Or allocate in blocks: each node gets a range (e.g., node 1: 1–1M, node 2: 1M+1–2M) — no replication contention, no failover gap. Or use UUIDs (no shared counter).

## Sequences and Caching

Sequences cache values per session for performance:

::code-wrapper{language="sql"}
```sql
CREATE SEQUENCE my_seq CACHE 20;
``

A CACHE of 20 means each session grabs 20 values at once (reducing the shared-counter contention). The cost: on session crash, the unused cached values are lost (gaps). For high-throughput inserts, a larger cache helps; for low-throughput, a cache of 1 (no caching) is fine.

Multi-tenant and Partitioned ID Strategies

For multi-tenant tables, a global IDENTITY is fine, but you might want per-tenant sequences (e.g., invoice numbers per tenant):

sql
-- Per-tenant invoice numbering (one sequence per tenant)
CREATE TABLE tenants (id BIGINT PRIMARY KEY, name TEXT);

CREATE FUNCTION next_invoice_number(tenant_id BIGINT) RETURNS BIGINT AS $$
DECLARE
  seq_name TEXT;
BEGIN
  seq_name := 'tenant_' || tenant_id || '_invoice_seq';
  EXECUTE 'CREATE SEQUENCE IF NOT EXISTS ' || seq_name;
  RETURN nextval(seq_name);
END;
$$ LANGUAGE plpgsql;
``
::

This is a simple (if hacky) per-tenant counter. For production, consider a `tenant_invoice_counters` table with row-level locking (`SELECT ... FOR UPDATE`) instead of dynamic sequences.

## 💡 Tips & Tricks

- **Idiom**: use `BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY` for new tables — it's the SQL-standard, properly-tracked equivalent of `BIGSERIAL`, with easier `ALTER`/`RESTART` and cleaner dump/restore. Reserve `SERIAL` for legacy.
- **Idiom**: use `UUID` (v4 via `gen_random_uuid()`, or v7 for time-ordered) when you need client-side ID generation (idempotent retries, distributed systems) or global uniqueness across databases — but accept the 16-byte size and index fragmentation cost. Don't use UUIDs just because they look "modern."
- **Idiom**: after a bulk load or `COPY` that inserted explicit IDs, **reset the sequence** with `setval(pg_get_serial_sequence('t', 'id'), (SELECT max(id) FROM t))` — otherwise the next insert collides with a manually-inserted ID.
- **Performance**: increase a sequence's `CACHE` for high-throughput insert tables — a `CACHE 1000` means each backend grabs 1000 values at once, reducing the shared-counter lock contention that can become a bottleneck on heavily concurrent inserts.
- **Reliability**: after a replica failover, advance the new primary's sequences past `max(id)` for every table — sequences don't replicate with logical replication, and a behind-the-data sequence causes immediate duplicate-key errors on the new primary.

## ⚠️ Edge Cases & Gotchas

- **Gaps are normal**: rolled-back inserts, failed inserts, crashes, and cached-but-unused values all create gaps. Sequences guarantee *uniqueness*, not *consecutiveness*. Don't try to fill gaps.
- **`currval` errors without a prior `nextval`**: `currval('seq')` returns the current session's last `nextval` — call `nextval` first, or it errors with "session does not have a current value for sequence."
- **`SERIAL` is not a type**: the column is `integer`/`bigint`; `SERIAL` is a declaration-time macro that creates a sequence + default + NOT NULL. `ALTER COLUMN col TYPE serial` is not valid.
- **`GENERATED ALWAYS` rejects manual inserts**: `INSERT INTO users (id, name) VALUES (100, 'x')` fails with "cannot insert a non-DEFAULT value into identity column" unless you add `OVERRIDING SYSTEM VALUE`. `GENERATED BY DEFAULT` allows it (with collision risk).
- **Sequence not reset after `COPY`/bulk insert**: if you insert explicit IDs (bypassing the default), the sequence stays at its old position — the next auto-insert may collide. Always `setval` after a data load.
- **`setval` semantics**: `setval(seq, N)` makes the next `nextval` return `N+1`. `setval(seq, N, false)` makes the next `nextval` return `N` (the `is_called` flag). Know which you want.
- **Sequences don't replicate (logical replication)**: replicas have independent sequence state. On failover, advance the sequence past `max(id)` to avoid duplicate keys.
- **UUIDv4 index fragmentation**: random UUIDs cause B-tree index fragmentation (random insert positions). For indexable UUIDs, use UUIDv7 (time-ordered, monotonic) — available via extensions or generated in the application.
- **`CACHE` values are lost on crash**: a `CACHE 1000` sequence reserves 1000 values per session; if the session crashes, the unused values are gone (gaps). For low-throughput tables, `CACHE 1` avoids this; for high-throughput, the gap tradeoff is worth it.
- **`OWNED BY` and column drop**: `ALTER SEQUENCE ... OWNED BY table.col` ties the sequence to the column — dropping the column drops the sequence. Without `OWNED BY`, the sequence survives column drop (orphaned).
- **`pg_get_serial_sequence`**: the reliable way to find a column's sequence name (`SELECT pg_get_serial_sequence('users', 'id')`) — don't assume the name is `users_id_seq` (it is for `SERIAL`, but `IDENTITY` and manually-created sequences differ).

## 🧠 Spot the Bug

A team migrates a `users` table by loading a dump with explicit IDs (1 through 10000). After the migration, new user registrations fail with "duplicate key value violates unique constraint." What happened?

::code-wrapper{language="sql"}
```sql
-- After loading the dump
-- The table's id column is BIGSERIAL PRIMARY KEY
-- The sequence users_id_seq is still at its old position (e.g., 1)
-- New insert: INSERT INTO users (name) VALUES ('new_user');
--   -> nextval('users_id_seq') returns 1
--   -> 1 already exists (from the dump) -> duplicate key error

::

Answer

The dump inserted rows with explicit IDs (1–10000), bypassing the id column's default (nextval('users_id_seq')). The sequence users_id_seq wasn't advanced — it's still at its pre-load position (e.g., 1). The next auto-generated insert calls nextval, gets a value that already exists in the table, and violates the primary key uniqueness constraint.

The fix — after any data load with explicit IDs, advance the sequence past the max:

SELECT setval(pg_get_serial_sequence('users', 'id'),
              (SELECT MAX(id) FROM users));

:: This sets the sequence to max(id), so the next nextval returns max(id) + 1 — no collision.

For an IDENTITY column, the equivalent:

ALTER TABLE users ALTER COLUMN id RESTART WITH (SELECT MAX(id) + 1 FROM users);
-- Or compute max first, then RESTART with the literal.

:: The lesson: explicit-ID inserts don't advance the sequence. After a data load/migration/COPY that supplies IDs, always reset the sequence to max(id), or the next auto-generated insert collides.

Summary

You can now choose between IDENTITY (modern, standard), SERIAL (legacy), and UUID (distributed), understand that gaps are normal and sequences aren't transactional, reset sequences after data loads, handle replication failover, and tune CACHE for throughput. Next: security, roles, and permissions.
